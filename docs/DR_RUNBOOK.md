# คู่มือซ้อมกู้คืนและกู้ระบบ (Blue OS 0.50.0)

> R9 · DEC-119 · Q-19 "ซ้อมกู้คืนหลังติดตั้ง Staging" · ใช้คู่กับ [STAGING_KATANA17.md](STAGING_KATANA17.md)
> ตัวอย่างใช้ path ของ Staging: `C:\xampp\htdocs\blue`, ฐานข้อมูล `blue_staging`, สำเนานอกเครื่อง `E:\BlueBackup`

## สิ่งที่ต้องมีเสมอ — ถ้าขาดอย่างใดอย่างหนึ่ง กู้คืนไม่ได้
| ของ | อยู่ที่ไหน |
|---|---|
| ไฟล์สำรอง `.bluebak` | `storage\backups` บนเครื่อง **และ** สำเนาใน `E:\BlueBackup` (นอกเครื่อง) |
| APP_KEY | password manager (ไม่ใช่บนเครื่องที่อาจเสีย) — ไฟล์สำรองเข้ารหัสด้วยกุญแจนี้ |
| fingerprint ของกุญแจ | จดไว้คู่กับ APP_KEY (จาก `doctor` บรรทัด `app key`) ใช้เทียบว่ากุญแจถูกตัว |
| รุ่นของ Blue ที่ใช้อยู่ | GitHub Releases ของ `Phichaphop/r-os` — กู้ลงรุ่นเดียวกันหรือใหม่กว่า |

## ทำเมื่อไร
| การซ้อม | เมื่อไร |
|---|---|
| A. ซ้อมในฐานข้อมูลแยก | หลังติดตั้ง · ทุกเดือน · ก่อนอัปเกรดรุ่น (`doctor` เตือนเมื่อเกิน 90 วัน) |
| B. ซ้อมกรณีเครื่องเสียทั้งเครื่อง | **หลังติดตั้ง Staging (Q-19)** · ปีละครั้ง · เมื่อเปลี่ยนที่เก็บสำเนานอกเครื่อง หรือเปลี่ยนวิธีเก็บ APP_KEY |
| C. กู้ระบบจริง | เครื่องเสีย / หาย / ฐานข้อมูลพัง |

## A. ซ้อมในฐานข้อมูลแยก (ประมาณ 5 นาที)
```
cd C:\xampp\htdocs\blue
C:\xampp\php\php.exe bin\blue backup:run
C:\xampp\php\php.exe bin\blue backup:drill --as=ชื่อผู้ใช้ผู้ดูแล
```
- drill โหลดไฟล์สำรองลงฐานข้อมูลแยก (`blue_staging_drill`) ไม่แตะฐานข้อมูลจริง
- drill ตรวจ 4 อย่าง:
  - ทุกตารางมีจำนวนแถวครบ
  - ส่งออกข้อมูลอีกครั้งแล้ว hash ตรงกับตอนสำรอง
  - เอกสารทุกไฟล์ตรง SHA-256
  - ข้อมูลที่เข้ารหัสเปิดได้ด้วย APP_KEY ปัจจุบัน
- ล้างฐานข้อมูลแยกทิ้งทุกครั้งหลังซ้อม
- ผลต้องเป็น `PASSED` · ทำในเว็บได้ที่เมนู **สำรองและกู้คืนข้อมูล** → เปิดชุดที่ "ตรวจแล้ว" → "ซ้อมกู้คืน (ฐานข้อมูลแยก)"

## B. ซ้อมกรณีเครื่องเสียทั้งเครื่อง — บน Katana เครื่องเดิม (ประมาณ 30–60 นาที)
ทำบนเครื่องเดิมได้ เพราะซ้อมด้วย Blue **ชุดที่สอง** ในโฟลเดอร์และฐานข้อมูลแยก ระบบจริงทำงานต่อได้ตามปกติ
หลักการคือใช้ **เฉพาะของที่จะเหลืออยู่ถ้าเครื่องเสียจริง**: สำเนาใน `E:\BlueBackup` + APP_KEY จาก password manager + zip จาก GitHub Releases

1. **จดเวลาเริ่ม** (= จุดที่ถือว่าเครื่องเสีย) และเวลาของไฟล์สำรองล่าสุดใน `E:\BlueBackup`
2. แตก zip รุ่นเดียวกับที่ใช้อยู่ไปเป็น `C:\xampp\htdocs\blue-dr`
   - โฟลเดอร์ใน zip ชื่อ `blue` ให้แตกไว้ที่อื่นก่อนแล้วเปลี่ยนชื่อเป็น `blue-dr`
3. สร้างฐานข้อมูลของชุดซ้อม (Shell ของ XAMPP → `mysql -u root -p`)
   ```sql
   CREATE DATABASE blue_dr CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   CREATE DATABASE blue_dr_drill CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   GRANT ALL PRIVILEGES ON blue_dr.* TO 'blue'@'localhost';
   GRANT ALL PRIVILEGES ON blue_dr_drill.* TO 'blue'@'localhost';
   GRANT ALL PRIVILEGES ON blue_dr.* TO 'blue'@'127.0.0.1';
   GRANT ALL PRIVILEGES ON blue_dr_drill.* TO 'blue'@'127.0.0.1';
   ```
4. เปิด `http://localhost/blue-dr/` แล้วติดตั้ง:
   - Staging / UAT, ฐานข้อมูล `blue_dr`, **ไม่มีข้อมูลตัวอย่าง**
   - ผู้ดูแลชื่อ `dr.admin`
5. เปิด `C:\xampp\htdocs\blue-dr\config\env.php`:
   - แทนค่า `APP_KEY` ด้วยค่าจาก **password manager** — ห้ามคัดลอกจากเครื่องจริง เพราะต้องการพิสูจน์ว่าสำเนาที่เก็บไว้ใช้ได้
   - **ห้ามตั้ง** `BACKUP_OFFSITE_PATH` ในชุดซ้อม เพราะจะทำให้สำเนาปนกัน
6. กู้คืน (ระบุโฟลเดอร์ได้ คำสั่งจะเลือกไฟล์ใหม่สุดเองจากเวลาในหัวไฟล์):
   ```
   cd C:\xampp\htdocs\blue-dr
   C:\xampp\php\php.exe bin\blue restore:fresh E:\BlueBackup --as=dr.admin
   ```
   - คำสั่งแสดงรหัสชุดสำรอง เวลาที่สร้าง และรุ่น แล้วให้พิมพ์วลี `RESTORE XXXXXX` ที่ขึ้นบนจอ
   - ระบบซ้อมกู้คืนไฟล์นั้นในฐานข้อมูลแยกก่อน ถ้าไม่ผ่านจะหยุดโดยไม่เปลี่ยนอะไร
   - ถ้าผ่าน จะโหลดข้อมูลเข้าระบบ โดยสำรองสภาพก่อนกู้ไว้ และย้อนกลับเองถ้าล้มเหลว
7. ถ้าขึ้น `Next: php bin/blue migrate --backup-confirmed` ให้รันคำสั่งนั้น แล้วรัน `C:\xampp\php\php.exe bin\blue doctor`
   - ชุดซ้อมจะขึ้น WARN `scheduler` และ `off-site copy` ได้ เพราะตั้งใจไม่ตั้งค่าสองอย่างนี้
8. **ตรวจผล:** เข้า `http://localhost/blue-dr/` ด้วย**บัญชีจริงของคุณ** (บัญชี `dr.admin` จะไม่มีแล้ว เพราะถูกแทนด้วยข้อมูลที่กู้มา) แล้วตรวจ:
   - จำนวนพนักงานเท่ากับระบบจริง
   - รายการล่าสุดที่รู้ว่ามีก่อนเวลาไฟล์สำรอง ยังอยู่ครบ
   - เปิดเอกสารแนบได้ 1 ไฟล์
   - ถ้ามีรอบเงินเดือนที่อนุมัติแล้ว ให้เปิดดูได้
9. **จดเวลาจบ:**
   - RTO = เวลาจบ − เวลาเริ่ม
   - RPO = เวลาเริ่ม − เวลาของไฟล์สำรองที่ใช้
10. **ลบชุดซ้อมทิ้งทันที** เพราะมีสำเนาข้อมูลจริง:
    ```sql
    DROP DATABASE blue_dr;
    DROP DATABASE blue_dr_drill;
    ```
    ลบโฟลเดอร์ `C:\xampp\htdocs\blue-dr` แล้วล้างถังขยะ
11. กรอกแบบบันทึกท้ายคู่มือ ให้ผู้รับผิดชอบระบบลงนาม (AI ลงนามแทนไม่ได้)

## C. กู้ระบบจริงเมื่อเครื่องเสีย
1. เตรียมเครื่องใหม่ตาม [STAGING_KATANA17.md](STAGING_KATANA17.md) ข้อ 1–6 (ใช้รุ่นเดียวกับไฟล์สำรองหรือใหม่กว่า)
2. ติดตั้งผ่านเว็บ (ข้อ 7) แบบ**ไม่มีข้อมูลตัวอย่าง** ตั้งผู้ดูแลชั่วคราว เช่น `dr.admin` — อย่าสร้างผู้ใช้หรือข้อมูลอื่นเพิ่ม
3. ใส่ APP_KEY เดิมจาก password manager ลงใน `config\env.php` (แทนค่าที่ตัวติดตั้งสร้าง)
4. เสียบไดรฟ์ที่มี `E:\BlueBackup` แล้วรัน
   ```
   cd C:\xampp\htdocs\blue
   C:\xampp\php\php.exe bin\blue restore:fresh E:\BlueBackup --as=dr.admin
   ```
5. ถ้าคำสั่งบอกให้ migrate → `C:\xampp\php\php.exe bin\blue migrate --backup-confirmed`
6. ใส่ `BACKUP_OFFSITE_PATH` ใน `config\env.php` อีกครั้ง และตั้งงานตั้งเวลา (คู่มือ Staging ข้อ 8)
7. `doctor` ต้องไม่มี FAIL → เข้าสู่ระบบด้วยบัญชีเดิม → แจ้งผู้ใช้ให้ตรวจข้อมูลที่ทำหลังเวลาไฟล์สำรอง ซึ่งต้องบันทึกใหม่
8. ทำ A (ซ้อมในฐานข้อมูลแยก) บนเครื่องใหม่หนึ่งรอบ

### เงื่อนไขที่ `restore:fresh` บังคับ
| เงื่อนไข | เพราะอะไร |
|---|---|
| ระบบต้องมีบัญชีเดียว (ผู้ติดตั้ง) | กู้แบบนี้แทนที่ข้อมูลทั้งหมด จึงยอมเฉพาะระบบที่เพิ่งติดตั้งและไม่มีอะไรให้เสีย · ระบบที่ใช้งานอยู่ต้องกู้ผ่านเว็บ ซึ่งมีผู้ดูแลคนที่ 2 อนุมัติ |
| `--as=` ต้องเป็นผู้ดูแลที่มีสิทธิ์กู้คืน | ระบุตัวผู้สั่ง |
| ไฟล์ต้องเปิดได้ด้วย APP_KEY ของระบบนี้ | ถ้ากุญแจไม่ตรง จะหยุดและแสดง fingerprint ทั้งสองค่า |
| พิมพ์วลี `RESTORE XXXXXX` ให้ตรง (6 ตัวแรกของ SHA-256 ของไฟล์) | กันการสั่งผิดไฟล์หรือสั่งโดยไม่ตั้งใจ · ใช้ `--confirm="RESTORE XXXXXX"` ในสคริปต์ได้ |
| ไฟล์ต้องมาจากรุ่นเดียวกันหรือเก่ากว่า | รุ่นเก่ากว่ากู้ได้แล้ว migrate ต่อ · รุ่นใหม่กว่าต้องติดตั้งรุ่นนั้นก่อน |
| ต้องซ้อมกู้คืนไฟล์นั้นผ่านก่อน | ไม่ผ่าน = ไม่เปลี่ยนอะไร |

audit ของระบบที่กู้มาบันทึก `backup.restored_fresh` พร้อมชื่อผู้สั่งจากบรรทัดคำสั่ง ไม่ระบุบัญชีผู้ติดตั้ง เพราะบัญชีนั้นไม่ได้อยู่ในข้อมูลที่กู้มา

### ปัญหาที่เจอบ่อย
| ข้อความ | ทำอย่างไร |
|---|---|
| `the file was made with key …, this installation has …` | APP_KEY ไม่ใช่ตัวเดิม → ใช้ค่าจาก password manager (เทียบ fingerprint) |
| `กู้คืนจากบรรทัดคำสั่งได้เฉพาะระบบที่เพิ่งติดตั้งใหม่ …` | ระบบนี้มีผู้ใช้มากกว่าหนึ่งคน → ติดตั้งใหม่ หรือกู้ผ่านเว็บ |
| `ไฟล์นี้มาจากรุ่นที่ใหม่กว่า …` | ติดตั้ง Blue รุ่นที่ระบุหรือใหม่กว่าก่อน |
| `ซ้อมกู้คืนไฟล์นี้ไม่ผ่าน …` | ไฟล์เสียหรือไม่ครบ → ลองไฟล์ที่เก่ากว่าในโฟลเดอร์ (ระบุชื่อไฟล์ตรง ๆ แทนโฟลเดอร์) |
| ภาษาไทยในหน้าต่างคำสั่งเป็นตัวอ่านไม่ออก | พิมพ์ `chcp 65001` ก่อน แล้วรันคำสั่งใหม่ |
| drill ขึ้น `blocked` | ผู้ใช้ฐานข้อมูลไม่มีสิทธิ์ในฐานข้อมูล `…_drill` → ทำ GRANT ตามข้อ B.3 |

## ผลซ้อมที่ AI ทำใน container ก่อนส่งรุ่น (ยังไม่ใช่ผลบน Katana)
ขั้นตอนเหมือนส่วน B: เครื่อง A ติดตั้ง → สำรอง (มีสำเนานอกเครื่อง) → ลบเครื่อง A ทั้งโฟลเดอร์และฐานข้อมูล → เครื่อง B ติดตั้งใหม่ + ใส่ APP_KEY ที่เก็บไว้ → `restore:fresh <โฟลเดอร์สำเนา>` → `doctor`

| รายการ | ผล |
|---|---|
| ข้อมูล | 354 ตาราง 30,775 แถว (ข้อมูลตัวอย่าง เพื่อให้มีปริมาณ) |
| เลือกไฟล์จากโฟลเดอร์ | เลือกชุดล่าสุดจาก 2 ชุดถูกต้อง |
| ตรวจความตรงกัน | CHECKSUM ของ `users` และ `employees` ตรงกับเครื่อง A · รหัสผ่านเดิมของบัญชีที่กู้มายังใช้ได้ |
| `doctor` บนเครื่อง B | ไม่มี FAIL (WARN ข้อมูลตัวอย่าง ตามที่ตั้งใจ) |
| RTO | 17 วินาที (container ปริมาณข้อมูลน้อย — บน Katana จะนานกว่า ให้จดค่าจริงในแบบบันทึก) |
